# Работа с форматами

## Локальные инструменты

Проверки текста и OOXML работают на Python 3.9+ со стандартной библиотекой.
Для создания DOCX удобно использовать `python-docx`, для PDF `reportlab` с
установленным шрифтом, поддерживающим кириллицу. Эти библиотеки не нужны
скриптам форматирования DOCX. Сначала используй доступные зависимости среды;
в Codex Desktop их можно найти через `load_workspace_dependencies`, если
инструмент доступен. Не привязывай навык к путям конкретного компьютера.

Для рендера DOCX требуется локальный LibreOffice, для страниц PDF нужен
Poppler (`pdftoppm`) или PyMuPDF. Отсутствие рендерера не отменяет доступных
проверок текста, но оставляет вёрстку непроверенной. Не заменяй просмотр
отчётом линтера.

Ниже `SKILL_DIR` означает абсолютный путь к установленной папке `document-craft`.
Имена входных файлов и выходных папок замени на реальные. Команды выполняет
агент; пользователю достаточно описать задачу.

## DOCX: создание и рестайлинг

Создавай заголовки и обычные абзацы стилями. Устанавливай чёрный цвет в стилях
и непосредственном оформлении, включая `Title`, `Heading`, `Hyperlink` и
`FollowedHyperlink`, если они есть. Убирай свойства `themeColor`, `themeTint`,
`themeShade`: значение `000000` рядом с ними может быть перекрыто темой.
Задавай размер страницы и поля явно по [профилю страниц](layout.md).
Не используй декоративные table styles. Если документ содержит библиографию
или ссылки на источники, прочитай [правила библиографии](bibliography.md).

После сохранения нового файла можно применить профиль скриптом:

```bash
python3 "$SKILL_DIR/scripts/docx_format.py" draft.docx monochrome.docx
python3 "$SKILL_DIR/scripts/docx_layout.py" monochrome.docx final.docx
python3 "$SKILL_DIR/scripts/docx_check.py" final.docx --profile monochrome --json
python3 "$SKILL_DIR/scripts/docx_layout_check.py" final.docx --json
python3 "$SKILL_DIR/scripts/text_check.py" final.docx --json
python3 "$SKILL_DIR/scripts/render_pages.py" final.docx --out-dir work/final-pages
```

`docx_format.py INPUT OUTPUT` не перезаписывает вход и существующий выход.
В режиме `--scope document` (по умолчанию) он задаёт чёрный цвет текста и
белый фон в поддерживаемых частях OOXML, очищает заливки и эффекты, убирает
стили таблиц и оформляет их границы. `--scope tables` меняет все таблицы,
включая вложенные, но не обычный текст вне них. Это тоже рестайлинг, а не
режим точечной правки текста.

Скрипт добавляет `cantSplit`, переводит точную высоту строки в минимальную и
сохраняет существующие признаки строк заголовка. Если у каждой таблицы,
включая вложенные, первая строка действительно шапка, можно добавить
`--header-rows 1`. Значение `0` снимает признаки шапок во всех таблицах.
Для таблиц с разной структурой задавай `w:tblHeader` при создании каждой
таблицы отдельно; скрипт не угадывает назначение строк.

Утилита сохраняет текст и поля и переносит остальные части ZIP без изменения
их содержимого. Она не рассчитывает ширину колонок и отступы, не исправляет
разрывы страниц, не редактирует цвета внутри изображений, диаграмм, VML и
внешних объектов. Сложные объекты требуют отдельного просмотра и правки.
Подписанные пакеты форматтер отвергает: изменение документа нарушает проверку
подписи. Не выдавай изменённую рабочую копию за подписанный оригинал.

`docx_layout.py INPUT OUTPUT` применяет профиль к обычному документу с одной
конечной секцией: A4, поля 30/10/20/20 мм, Times New Roman 14 пт, интервал 1,5,
красная строка основного текста 1,25 см (списки сохраняют свои отступы),
ограничение жирности и пустой первый лист без номера. Он заменяет активные
колонтитулы: сверху ничего, снизу только поле `PAGE`, начиная с видимого 2
на второй странице, по центру физического листа. Сноски остаются содержанием.
Ключи `--body-size 12` и `--right-margin-mm N` предназначены для явно заданных
пользователем отклонений, а не самостоятельного выбора агента.

Для этой цепочки `draft.docx` начинается сразу с содержательной части:
пустой лист вставляет `docx_layout.py`. Если первый пустой лист уже сделан
вручную, не добавляй ещё один; проверь структуру и выбери ручную настройку
либо подготовь рабочий вход без дублирующего пустого листа. Не удаляй
заполненную первую страницу или данные пользователя.

Утилита пишет новый файл и не перезаписывает вход или существующий выход.
Метка пустого титульного листа защищает от повторной вставки при следующем
запуске. Несколько разделов не поддерживаются: настрой их при создании или
внеси отдельную проверенную правку OOXML, не удаляя разделы. Не запускай
утилиту при точечной правке текста. При полном рестайлинге учти, что это
изменение колонтитулов, шрифта и начертания; исходные надписи в колонтитулах
больше не выводятся. Заголовки и подписи должны иметь осмысленные стили:
скрипт не угадывает роль каждого абзаца по его содержанию.

`docx_layout_check.py INPUT [--json]` проверяет поддерживаемую структуру
первого листа, настройки страницы, поля, шрифт, кегль, интервал, жирность и
активные колонтитулы. Он не доказывает, что рендерер действительно использовал
нужный шрифт, и не вычисляет фактическую пагинацию. Заявление «на второй
странице стоит 2» подтверждай просмотром рендера и извлечённым текстом PDF.

## DOCX: точечное редактирование

Сохраняй стили, размеры, поля, заливки, границы, колонтитулы и разбиение на
разделы исходника. Новые фрагменты оформляй по их роли в текущем документе.
Не запускай `docx_format.py` и `docx_layout.py` для обычной замены текста.

Не присваивай всему `paragraph.text` или `cell.text` новый текст: это может
уничтожить runs, ссылки и локальное оформление. Найди точный фрагмент в runs,
при необходимости обработай совпадение на их границе. Не пересобирай весь
документ из извлечённого текста. Для сложных файлов предпочитай узкую правку
OOXML с сохранением остальных частей пакета; `python-docx` может не сохранить
некоторые неподдерживаемые элементы при полном пересохранении.

Не принимай и не удаляй исправления и комментарии без запроса. Для полей,
сносок, закладок, ссылок и нумерации сохраняй связи, идентификаторы и коды.
После правки проверь видимый текст и изменённые части пакета:

```bash
python3 "$SKILL_DIR/scripts/docx_check.py" edited.docx --profile preserve --baseline original.docx --json
python3 "$SKILL_DIR/scripts/render_pages.py" edited.docx --out-dir work/edited-pages
```

Профиль `preserve` не считает исходные цвета нарушением. С базовым файлом он
показывает изменившиеся части пакета и различия последовательностей свойств
оформления. Это грубая диагностика: одинаковая последовательность свойств
не доказывает, что каждое свойство осталось у того же текста. Сравни текст,
затронутые элементы и страницы до/после. Без `--baseline` сохранность
оформления нельзя подтвердить этой проверкой.

## Контракты проверок

| Инструмент | Результат и код выхода |
|---|---|
| `docx_check.py INPUT [--json]` | Структурные ошибки, предупреждения, ограничения; `0` без ошибок, `1` есть ошибки, `2` сбой. Предупреждения могут остаться при коде `0`. |
| `docx_layout_check.py INPUT [--json]` | Проверка пользовательского профиля страниц и текста; `0` без ошибок, `1` есть ошибки, `2` сбой. Замечания по сложным элементам требуют просмотра. |
| `text_check.py INPUT [--json]` | Повторы, частые одинаковые вводные, незаполненные поля и технический мусор; `0` без находок, `1` нужен просмотр, `2` сбой. |
| `sanitize_text.py INPUT [--out NEW] [--json]` | Санитарная проверка UTF-8 Markdown/TXT; без `--out` только отчёт. С ним создаётся новая копия. `0` без нерешённых находок, `1` нужен просмотр, `2` ошибка ввода/записи. |
| `render_pages.py INPUT --out-dir DIR` | PNG всех страниц и `manifest.json`; `0` рендер завершён, `2` ошибка. Визуальная проверка остаётся `pending`. |

`docx_check.py --profile monochrome` ищет явные и тематические цвета,
заливки, выделения, оформление границ и наследуемые определения в стилях.
Проверка консервативна: может отметить неиспользуемый цветной стиль.
Не вычисляет полный каскад Word и не проверяет пиксели изображений.
`--scope tables` ограничивает анализ таблицами; для нового документа проверяй
весь документ. Все предупреждения требуют решения с учётом задачи.

`text_check.py` принимает UTF-8 `.md`, `.markdown`, `.txt` и извлекает текст из
`.docx`. Для DOCX номера строк относятся к извлечению, не к страницам.
Линтер пропускает код, цитаты и URL; прочитай их отдельно, если они входят
в область проверки. Сам текст не меняется, автоматической чистки нет.

Редакторский цикл описан в [anti-slop.md](anti-slop.md). Для новых текстов
сначала запусти санитарную проверку рабочей копии, затем русский линтер.
`sanitize_text.py` сохраняет русскую пунктуацию, символы формул, неразрывные
пробелы и мягкие переносы; управление направлением текста требует решения
при чтении. Для DOCX/PDF работай с извлечённой текстовой копией и возвращай
только разрешённые правки в редактируемый источник. Режим `format_only`
не разрешает такую обратную запись. Отдельного английского линтера или
внешнего сервиса для работы навыка не требуется.
При извлечении DOCX/PDF заранее выдели листинги, цитаты и формулы в рабочей
копии: форматирование источника при плоском извлечении не сохраняется.
Если защитить их надёжно нельзя, выполняй санитарную проверку без `--out`.

Для рендера выходная папка должна быть новой или пустой. Если инструменты
не в `PATH`, задай `--soffice /путь/к/soffice` и/или
`--pdftoppm /путь/к/pdftoppm`. Ключи `--dpi 144` и `--timeout 120` задают
разрешение и лимит секунд на внешний процесс. Встроенный временный профиль
LibreOffice отделён от пользовательского профиля. После рендера открой PNG
каждой страницы; после изменения создай новый рендер последней версии.

Если локальный рендерер не видит уже установленный Times New Roman, можно
передать `--font-dir /путь/к/каталогу/шрифтов` (повторяется для нескольких
каталогов). Скрипт создаст временную конфигурацию поиска шрифтов для дочерних
процессов, без изменения системных настроек и без копирования шрифтов.
Проверь фактические шрифты полученного PDF. Флаг не устанавливает отсутствующие
шрифты и не гарантирует, что в указанном каталоге есть нужная гарнитура.

## PDF

Для DOCX и PDF одного документа используй общий редактируемый источник:
сначала заверши DOCX, затем экспортируй его в PDF и проверь оба результата.
При прямом создании PDF встрой шрифт с кириллицей, задай чёрный цвет текста
и линий, белый фон и таблицы без заливки. Не полагайся на стандартные PDF
шрифты без проверки русских символов. В ReportLab повторяй реальные заголовки
через `repeatRows`, границы задавай `GRID` 0,5 пт, не добавляй `BACKGROUND`.

Профиль страниц, шрифта, первого листа и специальных элементов одинаковый
для DOCX и PDF. При прямом создании PDF сначала выведи пустую страницу без
номера, затем содержание с номером физической страницы 2. В callback
колонтитула выводи только номер при `pageNumber >= 2`, центрируя по ширине
всего листа. Не добавляй служебный заголовок или подпись о проверке источников.
Основной текст 14 пт, интервал 21 пт; сноски 10 пт, интервал 10 пт.

Для проверки извлеки текст локальным `pdftotext`, `pypdf` или `pdfplumber`,
прочитай его и передай UTF-8 файл в `text_check.py`. Затем:

```bash
python3 "$SKILL_DIR/scripts/render_pages.py" final.pdf --out-dir work/pdf-pages
```

Сверь порядок чтения, числа, ссылки, шрифты и все страницы. Проверь реальный
шрифт PDF (например, через локальный `pdffonts`), а не только название шрифта
в исходном DOCX. Если LibreOffice не видит установленный Times New Roman,
настрой локальный поиск шрифтов или сообщи о подстановке. Не скачивай и не
включай проприетарные шрифты в пакет навыка. Отсутствие текста
в скане не означает пустой документ; используй доступное локальное OCR и
сверяй распознавание по изображениям, особенно числа. Не выдавай OCR за точную
копию без проверки.

Точечное изменение готового PDF не всегда сохраняет переносы и шрифты.
Если есть исходник, редактируй его и экспортируй заново. Если исходника нет,
сначала оцени возможность локальной правки; не пересобирай весь PDF и не
заменяй его картинками молча. Заранее сообщи существенную неизбежную потерю
оформления; при необходимости уточни допустимый результат. Не добавляй
обязательный запрос исходника, если доступная правка уже решает задачу.

## Markdown

Пиши UTF-8, используй последовательную иерархию заголовков и обычные списки.
Не вставляй HTML/CSS для цвета, плашек и «карточек». Для простой таблицы
подходит GFM; экранируй `|` внутри ячеек. Длинные многострочные объяснения
лучше вынести в абзацы. Не изображай объединённые ячейки там, где синтаксис
их не поддерживает. Цветовую тему программы просмотра Markdown навык не задаёт.

При правках сохраняй стиль разметки, frontmatter, относительные ссылки и
блоки кода. Проверь diff и открытие локальных ссылок; URL проверяй при
необходимости и доступе к сети. Финальный линтер дополни чтением исходной
разметки и доступного предпросмотра. Для экспорта в PDF применяй отдельный
монохромный профиль и проверяй PDF как самостоятельный результат.
